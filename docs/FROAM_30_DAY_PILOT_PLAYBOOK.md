# Froam 30-Day Paid Pilot Playbook

## Goal

Sell and complete **five $49 assisted pilots** in 30 days.

The immediate revenue target is $245. The real objective is stronger: prove
that a specific user can install Froam, produce output, return to it, and name a
recurring problem worth paying to solve. Do not call this monthly recurring
revenue and do not advertise Froam Pro as available yet.

Run this alongside the separate $300+ done-for-you site-polish offer. The pilot
validates the product workflow; site polish sells an implementation result.

## The promise being tested

> Froam helps developers and freelancers finish the website they already have
> by editing the running page and saving the result as reviewable presentation
> files, without moving the project into another builder.

## Readiness gate

Before accepting the first payment:

- [ ] The published npm version and install command are written on the offer.
- [ ] A clean-folder install succeeds.
- [ ] Static HTML and local HTTP workflows produce the documented files.
- [ ] The demo shows edit, Save to Repo, generated files, reload, and undo.
- [ ] The compatibility report and selector-retargeting limitation are linked.
- [ ] The payment page uses the exact scope in `FROAM_ASSISTED_PILOT.md`.
- [ ] A simple intake form asks for URL, stack, ownership, and desired outcome.
- [ ] No page claims that $15/month Pro or hosted collaboration is available.

## Three proof demos

Keep each demo under 90 seconds and use a project you own or have permission to
edit.

### 1. Visual finishing

Open a working but plain page. Improve the heading, primary button, spacing, and
mobile presentation. End on the generated CSS diff.

### 2. A realistic revision

Change headline copy, replace an image, and apply a restrained entrance motion.
Show that content changes require the runtime file; do not describe them as
source-template edits.

### 3. Persistence and control

Save, refresh outside the editor, inspect the files, undo one edit, save again,
and refresh. This is the trust demo.

Every demo should put the same five labels on screen:

1. Edit the running page.
2. Save to Repo.
3. Inspect ordinary project files.
4. Refresh and verify.
5. Commit only when satisfied.

## Week 1 — prove and invite

- Complete the readiness gate.
- Record all three demos.
- Publish a small offer page using the exact $49 scope.
- Invite 20 qualified people individually; aim for conversations, not reach.
- Post one transparent build/demo in each community where self-promotion is
  allowed. Disclose that you made Froam and follow the channel's current rules.
- Book the first two sessions.

Priority audiences: freelancers using React or AI coding tools, developers with
an almost-finished marketing page, and technical founders actively shipping.
Communities may include relevant Claude Code, side-project, and vibe-coding
groups, but recheck each community's rules immediately before posting.

## Week 2 — onboard five people

- Run the 45-minute workflow from the pilot document.
- Log every setup failure and every moment that needs explanation.
- Fix only blockers repeated across sessions or severe trust failures.
- Ask participants to use Froam again without you within seven days.
- Keep support inside the stated two-thread boundary.

## Week 3 — remove the repeated obstacle

- Rank friction by how many pilots hit it and whether it prevented saved output.
- Fix the highest-frequency blocker.
- Re-record only the demo affected by the fix.
- Publish one permissioned case study showing the starting problem, generated
  output, shipped result, and the limitation disclosure.
- Ask participants for one introduction to a similar developer or freelancer.

## Week 4 — decide what is sellable

Review the evidence. Offer a $15/month Pro beta only if at least three pilots
independently ask for the same recurring capability, such as durable hosted
projects, review links, approvals, managed publishing, or managed AI.

If they value setup but do not return, keep selling assisted onboarding or move
the insight into the site-polish service. If they create output and return but
do not need cloud features, keep the package free and sell complementary help.

## Daily operating rhythm

Spend 30 focused minutes on distribution:

- five personal invitations to qualified people;
- one helpful answer, teardown, or short demo in a relevant community;
- one follow-up with someone who attempted installation;
- update the scorecard and friction log.

Do not mass-post identical copy, hide your ownership, or argue with people who
are not the target customer.

## Decision rules at day 30

- **Build Pro:** at least 3 of 5 paid pilots activate, at least 2 return within
  seven days, and at least 3 independently request the same recurring service.
- **Keep the package free and sell onboarding:** activation is good, but return
  usage or recurring demand is weak.
- **Lead with site polish:** buyers want the finished outcome and do not want to
  operate the tool themselves.
- **Pause acquisition and fix trust:** selector stability, output correctness,
  or installation blocks more than one pilot from shipping.

The first month is successful when it produces a clear decision backed by paid
behaviour, even if that decision is not a subscription.
